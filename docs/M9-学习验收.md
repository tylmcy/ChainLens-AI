# M9 交易评测学习验收

工程测试全绿不等于已经会设计和维护评测。请由维护者本人操作、解释并排错；助理可以提示，但不能代替独立复现。学习验收和 M9 工程交付分别记录。

## 先用大白话解释

1. 为什么 offline 评测能断网运行，而 full 评测必须访问实时 RPC 和模型？冻结的 JSON-RPC 响应与 ground truth 分别是什么？
2. 解析准确率 `585/585` 的分母是什么；规则准确率 `210/210` 为什么等于 30 笔 × 7 条规则？`applicable:false` 为什么不能被当作“正确”？
3. `ruleId`、`evidence` 和 `jsonPointer` 分别解决什么问题？为什么模型写得流畅，也不能替代原始交易回执？
4. 模型调用前为什么要预留费用；usage 缺失时为什么保留预留并停止，而不能填 0？报告中的费用估值为什么不等于最终账单？

## 独立复现与修改

1. 从 [`eval/cases/transaction-eval-v1.json`](../eval/cases/transaction-eval-v1.json) 挑一笔交易，找到对应 [`eval/fixtures/`](../eval/fixtures/) 里的 transaction、receipt、block、chain-id 和 code 响应。指出一个解析字段及一个 finding 的原始 JSON 位置，不借助模型回答。
2. 按 [README 的 offline 命令](../README.md#m9-离线交易评测当前可复现)自行运行门槛，打开 [`latest.json`](../eval/results/offline/latest.json) 核对分子、分母、TP/TN/FP/FN；能解释为什么固定样本 100% 不代表所有 Ethereum 交易 100%。
3. 阅读 `TransactionOfflineEvaluationGateTest` 的临时坏标注测试，亲自复现一项低于门槛的结果，指出失败的 `caseId` 和差异字段，并确认失败时 CI 的 `always()` 仍上传报告。不要改动正式 30 条 ground truth 或提交故障注入。
4. 运行 `ModelBudgetTest`，分别演示“下一次调用预留超预算”和“provider 不返回 usage”两条停止路径；说明报告中的已核实费用、不可核实预留和未执行用例的区别。这里使用 mock 价格，不调用付费模型。
5. 在临时工作分支中，为一个**合成测试用例**增加安全的解析或规则断言，运行对应单测；再故意让断言失败，依据差异排错并修正。不要改真实链上 fixture 来“调高”分数，也不要把真实 API Key 写进命令或 Git。
